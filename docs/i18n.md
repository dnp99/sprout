# Internationalization (i18n)

Sprout's UI is localized with [`next-intl`](https://next-intl.dev). The app ships four
locales — **`en-CA`** (default), **`fr-CA`** (beta), **`zh-Hans`**
(Simplified Chinese), and **`zh-Hant`** (Traditional Chinese) — with no locale segment
in URLs. Money and dates format per locale; the currency itself is always CAD
(only the *display* localizes, not what's stored). Design decisions and history
live in [`plans/completed/013-internationalization.md`](../plans/completed/013-internationalization.md).

## How the locale is chosen

The active locale is resolved **per request** — there is no mutable global.

1. The `sprout-locale-pref` cookie is the only persisted source of truth. Its
   value is a `LocalePref`: `"system" | "en-CA" | "fr-CA" | "zh-Hans" | "zh-Hant"` (see
   [`src/lib/locale.ts`](../src/lib/locale.ts)).
2. `"system"` (or a missing/garbled cookie) resolves against the request's
   `Accept-Language`, falling back to `en-CA`. Quality weights are respected (zero-quality
   entries are skipped). Chinese script tags win over regions; `zh-TW`,
   `zh-HK`, and `zh-MO` use Traditional, while bare `zh` defaults to Simplified.
3. [`src/i18n/request.ts`](../src/i18n/request.ts) reads the cookie + header and
   hands the resolved locale + messages to next-intl. Server Components read it
   via `getLocale()`/`getTranslations()`; Client Components via the provider.

### Route groups

`src/app` is split into two URL-transparent groups, each with its own root
layout (the shared shell is [`src/app/root-document.tsx`](../src/app/root-document.tsx)):

- **`(localized)`** — the authenticated app + auth gate. Wraps children in
  `NextIntlClientProvider`, sets `<html lang>` from the resolved locale, and seeds
  the store with `localePref` + `locale` so hydration matches the server.
  `LocaleSync` keeps those store fields fresh after a `router.refresh()`.
- **`(public)`** — landing, privacy, terms, security, data. **Always English**
  (`lang="en-CA"`), no provider. Marketing/legal translation is out of scope
  (legal needs counsel review).

Moving a page between groups does not change its URL.

### Changing language

The Settings → Language dropdown ([`LanguageToggle`](../src/components/shared/LanguageToggle.tsx))
writes the cookie, optimistically updates the store, and calls `router.refresh()`
so Server + Client Components re-render together. "Français (bêta)" is flagged
beta until the machine-first translations get a human review.

## Message catalogs

- [`src/messages/en-CA.json`](../src/messages/en-CA.json) is the **source of
  truth**; [`src/messages/fr-CA.json`](../src/messages/fr-CA.json) must mirror its
  key tree exactly, as must `zh-Hans.json` and `zh-Hant.json`.
- Keys are namespaced by surface: `nav`, `titles`, `budget`, `home`, `settings`
  (currently just `settings.language`), `dates`, `hero`, `checklist`,
  `discovery`, `overview`, `trends`, `settingsPage`, `importer`, `bills`,
  `goals`, `txns`, `addFlow`, `mobile`, `auth`.
- Use ICU syntax for counts/interpolation:
  `"{count, plural, one {# item} other {# items}}"`, `"{amount} due this month"`.
- `scripts/check-i18n-catalogs.mjs` runs inside `npm run lint` and **fails on
  drift** (a key present in `en-CA` but missing/extra elsewhere). Add every new
  key to all four files. The Chinese catalog tests also compile every ICU
  message and verify interpolation arguments and rich-text tags.

## Formatting

All display formatting is locale-aware and takes the locale **explicitly** so
the helpers stay pure and testable ([`src/lib/format.ts`](../src/lib/format.ts)):

- **Money** — `formatMoney(cents, { locale, signed, forceCents })`. Currency is
  always `CAD`; `en-CA` → `$4,958.02`, `fr-CA` → `4 958,02 $`. Money is only ever
  converted to a display string here — never `amount / 100` in a component.
- **Input** — `parseMoneyInput(value, locale)` is the symmetric parser: it
  discovers the locale's decimal/group separators via `Intl`, accepts the
  no-break-space family for fr-CA grouping, enforces thousands boundaries, and
  returns `null` for ambiguous/negative/malformed input.
- **Dates** — the `formatMonth*/formatShort*/formatWeekday*` family replaces
  every inline `toLocaleDateString`. Transaction dates are UTC calendar dates:
  month scopes, row labels, and edit inputs all use the UTC day so an imported
  midnight timestamp cannot appear in the prior local day.

In client components, prefer the [`useFormatters`](../src/i18n/useFormatters.ts)
hook — `fmt.money(...)`, `fmt.monthKey(...)`, `fmt.txnDate(...)`, etc. — which
injects the active locale for you. Pure libs and Server Components pass the
locale directly.

### Data, not prose, from the API

Display strings are formatted at the edge, not on the server: the transaction
`dateLabel` and summary `monthLabel` are derived client-side from the raw
`occurredAt` / month key, so they follow the viewer's locale.

## Adding a string

1. Add the key to **all four catalogs** (`en-CA.json`, `fr-CA.json`, `zh-Hans.json`, `zh-Hant.json`) under the right
   namespace (English value = the exact copy you're replacing).
2. In the component: `const t = useTranslations("<namespace>")`, render `{t("key")}`.
   For money/dates use `useFormatters`, not a hard-coded locale.
3. Run `npm run lint` (catalog check) and `npm run test`.

## Known English-only surfaces (intentional)

- **Landing, marketing, and legal pages** — `(public)` group; legal needs counsel
  review, marketing waits on a translation decision.
- **The Siri/WhatsApp capture setup guide**
  ([`CaptureSetupGuide`](../src/components/settings/CaptureSetupGuide.tsx)) — a
  technical API-setup walkthrough. Its prose remains English, but capture input
  supports multiple languages independently of the UI (see below).
- **Server-side API error messages** — returned in English; known error `codes`
  can be mapped to translated client copy where it matters.

## Multilingual transaction input

UI language controls interface copy and display formatting only. Merchant names,
category names, notes, CSV content, and receipt text retain their original script;
switching language never translates or rewrites stored data. Users can enter
Chinese in an English/French interface and English in a Chinese interface.

Siri/WhatsApp text capture shares a locale-independent parser. Common English,
French, Simplified Chinese, Traditional Chinese, and mixed-language phrases work
without an AI key. Unicode merchant names are retained; common Chinese income
and expense words, 今天/昨天, full-width digits, decimal commas, and explicit
Chinese currency amounts such as 十二元五角 are recognized. Examples:

- `今天午饭花了35元` → expense, −3500 cents, merchant 午饭, today.
- `昨天收到公司薪資八千元` → income, +800000 cents, merchant 公司, yesterday.
- `coffee 咖啡 12.50 CAD` → expense, −1250 cents, merchant Coffee 咖啡.

More complex input uses the existing multilingual AI fallback when configured.
Ambiguous amounts, multiple numeric tokens (including explicit calendar dates),
and missing amounts go to that fallback; if unavailable, capture requests ask
for clarification rather than writing a guessed amount. Currency words are
input grammar only: stored money remains integer CAD cents, with no exchange
rate conversion. See [capture-api.md](capture-api.md).

Merchant rule matching uses Unicode letters and numbers rather than an ASCII-only
filter, so distinct Chinese merchants do not collapse to an empty/shared key.
ASCII store/reference suffix removal stays compatible. Existing merchant rules
are not rewritten; new Chinese rules retain their nonempty merchant key.
